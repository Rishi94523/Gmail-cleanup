# Architecture

The same Node service serves the React landing page, workspace, OAuth callback and API. Cloud Run uses Neon PostgreSQL and Secret Manager. Local development uses SQLite and environment keys. NVIDIA Nemotron 3.5 Super VL is called only through Nebius Token Factory; no alternate model provider is enabled.

## Agent flow

The agent is the only cleanup path, and it works on unread Primary mail. Promotions, Social and the other Gmail tabs are already sorted by Gmail, so the app does not reclean them; the earlier rules-only cleanup (age/category filters with a manual preview) was removed. Scheduled runs skip accounts whose agent is not set up.

- Gmail category labels are hints rather than a veto on a Primary search result. If another category label is present, discovery and cleanup confirm the exact message with a Primary/unread/inbox search scoped to its Message-ID; ambiguous or missing identities stay unchanged. Cleanup repeats the scope check before writing and still requires an unchanged Gmail history ID. The scope-check version is part of the assessment fingerprint, so skips from an older scope rule can be assessed again without deleting audit history.

- Discovery freezes the initial Primary sample before cleanup. It sends header metadata in groups of 25, with two model requests at a time. Evidence-backed broad topics are deduplicated before questions are saved.
- Topic preferences and written conditions are encrypted, versioned and editable. Sender exceptions take precedence. Saved preferences apply to every eligible older or newer email in both manual and daily cleanup. Save/update timestamps are audit metadata only, never eligibility cutoffs. Only explicit topic age conditions (for example security notices older than 30 days) restrict message age, measured against the current time. Resolved and no-question holds can be reassessed on the next run; unanswered and snoozed questions remain protected. Standalone preference edits do not run cleanup. Answer submissions commit the preference first, then immediately run a question-scoped held cleanup.
- Written onboarding or workspace instructions are interpreted into a preview and explicitly confirmed. The preview is encrypted, account-bound, expires after 20 minutes and checks preference versions before saving. Background notes preserve the user's words and inform discovery/cleanup without granting action permissions. When confirmed notes resolve a pending question, they trigger the same held-only follow-up; other preference changes wait for manual or scheduled cleanup.
- Cleanup fetches 20-message windows, asks for two concurrent batches of ten decisions, then rechecks permissions and labels before serial Gmail writes. A model decision cannot override protected labels or user permissions.
- Unclassified model decisions get at most one focused clarification pass for only those items. The model can match an existing saved topic, propose a new broad preference question, or judge mail that fits no topic against the general action ("When an email doesn't matter") with at least 0.75 confidence (saved topics need 0.8 for both the category match and the action; gates are calibrated to Nemotron, which rates clear decisions around 0.75–0.9). Such mail is never silently held; below the gate it is kept and reassessed when preferences or `AGENT_DECISION_VERSION` change. Uncertainty never grants action permission, and sensitive-notice, protected-label and sender-exception rules still apply. Per-request aliases and identity validation also apply to the retry. The all-eligible applicability policy is recorded in the encrypted run log and assessment fingerprint.
- Answer-triggered cleanup uses an immutable snapshot of held IDs belonging to the signed-in account and answered question/category, processed in batches of 100 under the answer request's account lock. It never performs a general inbox candidate search. The server awaits the work rather than starting a detached background promise; the response reports the cleanup result. Pending/snoozed holds and uncertain Gmail writes remain excluded. Free-trial follow-ups can only revisit previously counted IDs in the original sample and do not increment usage again. A failure preserves the saved answer and audit records; duplicate answer submissions cannot start a second run.
- Mail deferred only by an explicit minimum age is not permanently cached as assessed; it can become eligible as it ages without changing the preference.
- Changes are reserved before external writes and confirmed afterward. Uncertain writes are not replayed. Undo restores only labels/read state that the run changed, for 30 days; after that the change rows keep only the message ID.
- Uncertain topics use `ask_preference`; the email is held unchanged and the agent continues. Pending questions persist until the user answers or snoozes them.
- Automatic unsubscribe is separately enabled and limited to verified one-click endpoints. DNS/address restrictions and signed headers prevent arbitrary network actions. There is no general browser or shell tool exposed to email content.

## Daily execution

Accounts choose 1–3 runs per day (`runsPerDay`, default 1), evenly spaced across 24 hours from the start hour in the account's timezone. Each run has a claim key that sorts in time order (`2026-10-29`, `2026-10-29#2`, `2026-10-29#3`); a cycle that crosses midnight keeps its start date. The scheduler runs an account only when its newest due key is later than `last_day`, so retries, replicas and changing the run count never repeat a run. Onboarding turns daily cleanup on when setup finishes for accounts allowed daily runs.

Local development uses an in-process minute timer. Cloud Run uses Cloud Scheduler every five minutes, with a Google-signed OIDC identity token verified for the exact audience and expected scheduler service account. Only users who enabled daily cleanup are eligible. A database lease and an account-local daily claim prevent duplicate runs across replicas and retries. The browser can be closed, and the service can scale to zero between requests.

The account's rules JSON stores `dailyPausedUntil`: 0 for no pause, -1 until resumed, or an absolute timestamp for 1/7/30-day pauses. Scheduler eligibility and active daily runs check the pause; skipped accounts do not claim the day. A CSRF-protected pause/resume endpoint preserves the schedule, preferences and onboarding consent. Pauses do not block manual runs or enable an otherwise disabled routine. No schema migration is required for existing accounts.

`HACKATHON_MODE=true` enables repeat manual runs and daily cleanups, capped at 100 Primary emails per run. The retained commercial allowance code is inactive in this mode; it is not a payment system. Account/model concurrency remains bounded. This demo deployment is not a verified thousand-concurrent-user capacity claim.

## Storage and observability

OAuth tokens, discovery/sample context, learned preferences, example subscription subjects and cleanup deltas use AES-256-GCM encryption. Sessions and account data are scoped per user. CSRF checks protect browser writes; the scheduler uses its separate authenticated endpoint.

Scheduler maintenance prunes data nothing reads again, at most hourly: rows left by the removed rules-only preview flow, agent decision logs beyond the latest 10 per account, change payloads past the 30-day undo window, and preference history older than 180 days. Runs, held messages, assessment markers and uncertain changes are kept because they prevent repeated processing or repeated model calls.

Operational logs report durations, token/cache counts and failure statuses without email text, subjects or credentials. Schema changes live in versioned SQL migrations; validate them on an expiring Neon branch before production.


### Performance diagnostics

Workflow tracing is enabled by default (`PERFORMANCE_LOGGING=false` disables it). `account_operation` spans cover the account lock and its DB work; discovery and cleanup have child traces with parent trace IDs. Cleanup traces include run IDs; classification calls include batch IDs and initial/clarification pass labels. `classification_retry_selection` records retry and unknown counts explicitly. An intentional unknown category does not cause clarification; malformed output and low-confidence named topics can still receive one bounded retry.

Structured start/completion events time Gmail/OAuth requests (normalized routes with no IDs or queries), full email preparation, model calls, SQL operations (statement hashes and verbs only), pool acquisition, and transaction controls. Stage/decision progress provides per-email progress without subjects or reasons. Existing AI usage events include trace/batch IDs, token/cache counts and elapsed time. Each workflow ends with wall time and operation counts, totals, maxima and failures. Totals overlap when spans nest or execute concurrently, so they must not be added to estimate wall time. DB query time includes pool acquisition for pooled queries; pool-wait spans show that portion separately. Model reasoning settings and output limits are unchanged. No prompts, responses, SQL text/parameters, mailbox IDs, account addresses or credentials are logged.

Nemotron 3.5 Super VL requests medium thinking by default (`NEBIUS_REASONING_EFFORT=medium`): `reasoning_effort: medium` and `chat_template_kwargs: {enable_thinking: true, medium_effort: true}`. `regular` omits both controls for a baseline comparison. AI timing events record the requested mode; acceptance alone does not prove that a provider honored template controls. The 50,000-token ceiling and 120-second request timeout remain unchanged.

Cleanup batches now drain in completion order: each fully validated batch is applied without waiting for its sibling. Failed batches never authorize writes; successful sibling batches are still applied before the run is marked partial. Outstanding model calls are drained before releasing the account lock, including if applying a decision fails. Progress distinguishes Gmail messages fetched from decisions completed; it never increments the checked count merely because metadata arrived. This uses complete JSON batch responses, not speculative actions on partial JSON tokens.

The deployed model can be selected with `NEBIUS_MODEL=nvidia/Nemotron-3-Ultra-550b-a55b`, served from the us-central1 endpoint. This is the Ultra 550B ID returned by the Nebius catalog; the Super-only medium chat-template setting is not sent to Ultra. Ultra currently uses provider-default reasoning, with the same 120-second timeout and 50,000-token ceiling.
